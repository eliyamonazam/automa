# معماری Automa

این سند معماری فنی سیستم رو تعریف می‌کنه. هر تغییر مهم در معماری باید اینجا و در `DECISIONS.md` ثبت بشه.

## اصول پایه

1. **هسته کوچک، لایه‌های افزودنی.** قلب سیستم یک حلقه‌ست: هدف ← برنامه ← اجرا ← راستی‌آزمایی ← اصلاح. بقیه قابلیت‌ها (Router، حافظه، ساخت Skill، …) لایه‌هایی روی این حلقه‌ان.
2. **اجماع جای راستی‌آزمایی رو نمی‌گیره.** هر وظیفه معیار پذیرش (acceptance criteria) داره و ارزیابی مستقل انجام می‌شه. هر جا ممکنه، ارزیابی با چیزی بیرون از مدل انجام می‌شه: اجرای تست، اجرای برنامه، بررسی فایل.
3. **محدودیت‌های حیاتی در کد اعمال می‌شن، نه در prompt.** سقف بودجه، سطح دسترسی ابزارها و نقاط تأیید انسانی قوانین کدن، و هیچ Agentی نمی‌تونه دورشون بزنه.
4. **همه‌چیز قابل ادامه‌ست.** وضعیت پروژه بعد از هر قدم روی دیسک ذخیره می‌شه.
5. **مستقل از ارائه‌دهنده.** همه فراخوانی‌های مدل از یک درگاه واحد (`LLMGateway`) رد می‌شن.

## نمای کلی

```
                 ┌──────────────────────────┐
  کاربر ── CLI ─►│   Orchestrator (حلقه)    │◄── Approval Gate ◄── کاربر
                 └──────────┬───────────────┘
        ┌───────────────────┼─────────────────────┐
        ▼                   ▼                     ▼
  Executive Agent     Worker Agents          Verifier Agent
  (برنامه‌ریزی)        (اجرای وظایف)          (ارزیابی مستقل)
        │                   │                     │
        └─────────┬─────────┴──────────┬──────────┘
                  ▼                    ▼
            LLMGateway            Tool Layer
       (مدل‌ها + Router)      (فایل، shell، git، وب …)
                  │                    │
                  ▼                    ▼
           Budget Guard          Permission Policy
           + Cost Ledger
                  │
                  ▼
           Project Store  (state، وظایف، خروجی‌ها، لاگ)
```

## اجزا

### CLI
`automa new "<هدف>"` تنظیمات رو می‌خونه، **قبل از ساخت پروژه** نگاشت سطح Executive و کلید API رو بررسی می‌کنه (تا پروژه یتیم نمونه)، پروژه رو می‌سازه، سؤال‌های روشن‌کننده Executive رو از کاربر می‌پرسه (`--no-ask` برای رد کردن)، پاسخ‌ها رو در `clarifications.json` ذخیره و `plan.json` رو با `plan_project` می‌نویسه. Provider فقط از `automa.llm.factory.provider_from_config` ساخته و فقط به `LLMGateway` با `BudgetGuard` روی Ledger مشترک workspace و `events.jsonl` پروژه داده می‌شه. `automa status [id] [--json]` فقط‌خوندنیه: نه کلید می‌خواد، نه فراخوانی مدل داره، نه فایلی (حتی Ledger) می‌سازه. `automa run <id> [--max-attempts N] [--parallel N] [--force]` پروژه برنامه‌ریزی‌شده رو با `Orchestrator` اجرا می‌کنه یا بعد از هر توقف ادامه می‌ده (همون دستور دوباره): قبل از هر کاری پروژه، وجود `plan.json` و وضعیت رو بررسی می‌کنه (پروژه `running` فقط با `--force`، چون ممکنه اجرای دیگه‌ای فعال باشه)، بعد کلید/Provider و نقش‌ها؛ Worker و Verifier روی همون Gateway محافظت‌شده ساخته می‌شن. خروجی: وضعیت و دلیل، تلاش‌های این اجرا، وظایف `passed`/`failed`/`blocked`، محل توقف با راهنمای قدم بعد، و هزینه این اجرا و کل از Ledger. Ctrl+C پروژه رو `paused` می‌ذاره. کدهای خروج ثابت: ۰ موفق، ۱ خطای کاربر، ۲ تنظیمات، ۳ توقف بودجه (پروژه `paused`)، ۴ شکست برنامه‌ریزی، ۵ خطای Provider، ۶ شکست قطعی وظیفه، ۷ توقف به دلایل دیگه (تأیید، ارزیابی، Tool Layer)، ۱۳۰ قطع با Ctrl+C (جزئیات: D16، D24). `automa bench list [--suite DIR]` فقط‌خوندنیه و `automa bench run <id> [--suite DIR] [--results DIR]` یک benchmark رو اجرا و ثبت می‌کنه (بخش «مجموعه آزمون»)؛ کد خروج ۸ یعنی اجرا ثبت شد ولی همه معیارهای موفقیت برآورده نشدن. `automa bench report [--benchmark ID] [--results DIR] [--json]` فقط‌خوندنیه و نتیجه‌های ثبت‌شده رو تحلیل می‌کنه (کد خروج ۱ اگه فایل نتیجه‌ای قابل استفاده نبود).

### Orchestrator
حلقه اصلی. وضعیت پروژه رو می‌خونه، وظیفه بعدی آماده (وابستگی‌هاش انجام‌شده) رو برمی‌داره، به Worker مناسب می‌ده، نتیجه رو به Verifier می‌ده، و بر اساس نتیجه وظیفه رو «انجام‌شده»، «برگشت برای اصلاح» یا «شکست» علامت می‌زنه. بعد از هر قدم state ذخیره می‌شه.

وظایف بی‌وابستگی به هم می‌تونن موازی اجرا بشن (M6، `max_parallel`).

**اجرای موازی (`OrchestratorSettings.max_parallel`، پیش‌فرض ۱):** با مقدار بیشتر از ۱ (سقف `MAX_PARALLEL` = ۸)، حداکثر `max_parallel` وظیفه آماده (همه وابستگی‌ها `passed`) هم‌زمان، هر کدوم در یک thread از `ThreadPoolExecutor`، با دقیقاً همون قدم‌های حلقه ترتیبی جلو می‌رن (`_drive` ← `_step` تا تموم شدن وظیفه). انتخاب وظیفه، بلاک کردن وابسته‌های وظیفه شکست‌خورده و وضعیت پروژه فقط در thread اصلی انجام می‌شه؛ هر thread فقط state وظیفه خودش رو می‌نویسه. اولین توقف (`budget`، `approval`، …) یا خطای غیرمنتظره زمان‌بندی رو تموم می‌کنه؛ وظایف در حال اجرا قدم فعلی‌شون رو (بدون قطع وسط فراخوانی) تموم می‌کنن، بعد پروژه با توقف اول `paused` می‌شه (توقف‌های بعدی ← رویداد `orchestrator.task_stopped`؛ خطای غیرمنتظره بعد از تخلیه بالا می‌ره). سقف خرج همچنان فقط با `BudgetGuard` مشترکه که هر فراخوانی هم‌زمان رو با رزرو بدترین حالت قبل از اجرا می‌سنجه. رویداد جدید `orchestrator.scheduled` و `max_parallel` در `orchestrator.started`. همه `JsonlEventLog`های یک مسیر در یک پروسه یک قفل مشترک دارن تا خط‌های رویداد قاطی نشن (جزئیات: D35).

**پیکربندی اجرای موازی (`config.py`، D36):** بخش `[orchestrator]` در `automa.toml` با `max_parallel` (۱..`MAX_PARALLEL`، پیش‌فرض ۱؛ کلید ناشناخته رد می‌شه). `MAX_PARALLEL` حالا در `config.py` تعریف شده و `orchestrator.py` همون رو استفاده می‌کنه تا مرزها یکی باشن. `automa run <id> --parallel N` برای همون اجرا جایگزین مقدار فایل می‌شه؛ مقدار نامعتبر (گزینه یا فایل) قبل از ساخت Provider و هر فراخوانی/Ledger رد می‌شه. `automa run` خط `parallel: …` چاپ می‌کنه و `automa status` (متن هر دو حالت و `max_parallel` در JSON یک پروژه) مقدار تنظیم‌شده رو نشون می‌ده؛ برای بیشتر از ۱ توضیح می‌ده که `files/` مشترکه و نوشتن فرمان‌ها (`run_command`) بررسی نمی‌شه. `automa bench run` عمداً ترتیبی می‌مونه (نتایج قابل مقایسه).

**تداخل فایل‌ها در اجرای موازی (`tools/claims.py`، D37):** دو لایه، فقط وقتی `max_parallel` > ۱:
1. *زمان‌بندی:* مسیرهای اعلام‌شده یک وظیفه (`declared_paths`: مسیرهای چک‌های `file_exists`/`file_contains` در معیارهای پذیرش) با مسیرهای اعلام‌شده وظایف در حال اجرا مقایسه می‌شن؛ اگه هم‌پوشانی داشته باشن (یک مسیر، یا یکی داخل دیگری) وظیفه منتظر می‌مونه تا اون یکی تموم بشه (رویداد `orchestrator.deferred`، یک بار برای هر وظیفه). وقتی هیچ وظیفه‌ای در حال اجرا نیست، اولین وظیفه آماده همیشه زمان‌بندی می‌شه، پس بن‌بست پیش نمیاد.
2. *اجرا:* هر `ToolExecutor` وظیفه یک `PathClaims` مشترک اجرا می‌گیره. ابزار با `Tool.writes(args)` مسیرهایی رو که می‌نویسه/حذف می‌کنه اعلام می‌کنه (`write_file`، `delete_file`)؛ Executor بعد از Policy و اعتبارسنجی آرگومان‌ها و **قبل از** Approval Gate و اجرای ابزار اون مسیرها رو برای وظیفه claim می‌کنه. اگه وظیفه دیگه‌ای که الان در حال اجراست مسیر هم‌پوشان رو داشته باشه، فراخوانی با خطای قابل فهم برای مدل شکست می‌خوره (رویداد `tool.path_conflict`) و فایل دست نمی‌خوره. claimها وقتی `_drive` وظیفه برمی‌گرده (تموم، توقف، شکست یا خطا) آزاد می‌شن، پس نتیجه همیشه معادل یک ترتیب ترتیبی از همون نوشتن‌هاست و وظیفه وابسته می‌تونه فایل وظیفه قبلی رو ویرایش کنه.
حالت ترتیبی (`max_parallel` = ۱) هیچ claim و تعویقی نداره و رفتارش عوض نشد. فایل‌هایی که `run_command` می‌سازه بررسی نمی‌شن.

**پیاده‌سازی (`src/automa/orchestrator.py`):** `Orchestrator(store, worker, verifier, roles, config, settings=…)` و `run(project_id) -> RunReport`. هر دور: وظایف `failed`/`blocked` همه وابسته‌های ناتموم‌شون رو `blocked` می‌کنن؛ اولین وظیفه ناتموم (به ترتیب topological) که همه وابستگی‌هاش `passed`ن انتخاب می‌شه. اگه آخرین تلاش ذخیره‌شده Verdict نداره (کرش یا `VerificationFailed`)، همون نتیجه دوباره ارزیابی می‌شه و Worker دوباره اجرا نمی‌شه؛ وگرنه تلاش جدید با ایرادهای Verdict قبلی به‌عنوان feedback، ذخیره `TaskResult`، ارزیابی، ذخیره `Verdict`. `pass` ← `passed`؛ `fail` ← `pending` برای تلاش بعدی، و بعد از `escalate_after` (پیش‌فرض ۲) رد پشت‌سرهم در یک سطح، سطح بالاتر **پیکربندی‌شده** (`small` < `medium` < `large`) در `TaskState.tier` ذخیره می‌شه؛ بعد از `max_attempts` (پیش‌فرض ۴، همه سطح‌ها با هم) ← `failed`. وقتی وظیفه‌ای نمونده، پروژه `done` (همه `passed`) یا `failed`. توقف‌ها پروژه رو `paused` می‌کنن و `RunReport.reason` می‌دن: `budget` (هر `BudgetError`، بدون تکرار)، `approval` (`ApprovalRequired`، ابزار اجرا نمی‌شه)، `provider`، `verification`، `tool_layer`، `config`؛ خطای Worker هیچ تلاشی مصرف نمی‌کنه (وظیفه ← `pending`). خطای غیرمنتظره پروژه رو `paused` می‌کنه و بالا می‌ره. Executorها فقط از `role.policy()` و `verifier_policy()` ساخته می‌شن. رویدادها: `orchestrator.started`/`attempt`/`escalated`/`paused`/`finished`. نقش ناشناخته ← وظیفه `failed` بدون فراخوانی مدل (جزئیات: D23).

### Executive Agent
- ورودی: هدف کاربر.
- ابتدا سؤال‌های روشن‌کننده (در صورت لزوم) تولید می‌کنه.
- خروجی: یک **برنامه** به شکل JSON: فهرست وظایف، هر کدوم با `id`، `title`، `role`، `inputs`، `depends_on`، `acceptance_criteria`.
- وقتی یک وظیفه چند بار شکست بخوره، Executive می‌تونه برنامه رو بازنویسی کنه (re-plan).
- **مدل‌های داده (`src/automa/plan/models.py`):** `Plan` (`schema_version`، `version`، `goal`، `tasks`) با اعتبارسنجی گراف (شناسه یکتا، وابستگی شناخته‌شده، بدون چرخه) و `topological_order`/`ready_tasks`/`dependents`؛ `Task` (`id`، `title`، `description`، `role`، `tier`، `inputs`، `depends_on`، `acceptance_criteria`)؛ `AcceptanceCriterion` با `check` اختیاری (`file_exists`، `file_contains`، `command`)؛ `TaskResult` (خروجی یک تلاش Worker) و `Verdict` (نظر Verifier، `pass`/`fail` + `checks` + `issues`، همیشه سازگار). مسیرها نسبی به `files/` و بدون `..`. `parse_plan` خروجی مدل رو اعتبارسنجی می‌کنه و `PlanError.details` بازخورد قابل فرستادن به مدل برای تلاش مجدده (جزئیات: D14).
- **پیاده‌سازی (`src/automa/agents/executive.py`):** `ExecutiveAgent` فقط با `LLMGateway` (یعنی همیشه از Guard رد می‌شه) ساخته می‌شه. `clarify(goal)` حداکثر ۵ سؤال برمی‌گردونه (فهرست خالی = بدون سؤال)؛ `plan(goal, clarifications)` یک `Plan` معتبر می‌ده. پاسخ نامعتبر (JSON خراب، گراف نامعتبر، نقش خارج از `known_roles`، پاسخ بریده‌شده با `finish_reason=length`) با فهرست خطای `PlanError.details` به مدل برمی‌گرده و حداکثر `max_attempts` (پیش‌فرض ۳، سقف ۵) بار تکرار می‌شه، وگرنه `PlanningFailed`. خطاهای Gateway (`BudgetExceeded`، `ProviderError`) هیچ‌وقت تکرار نمی‌شن. `goal` و `version` برنامه رو کد تعیین می‌کنه نه مدل. رویدادها: `executive.questions`، `executive.reply_rejected`، `executive.plan_ready`. `plan_project(agent, store, id)` برنامه رو در `plan.json` می‌نویسه و وضعیت پروژه رو مدیریت می‌کنه (`planning`؛ شکست ← `failed`؛ توقف بودجه ← `paused`) (جزئیات: D15).

### Worker Agents و نقش‌ها (Roles)
هر نقش یک فایل در `roles/` داره: دستورالعمل سیستمی، ابزارهای مجاز، سطح مدل پیش‌فرض. نقش‌ها داده‌ان، نه کد؛ پس اضافه کردن نقش جدید نیاز به تغییر کد نداره. نقش می‌تونه فهرست `skills` داشته باشه که فقط متن به پیام سیستمی اضافه می‌کنه و مجوزی نمی‌ده (بخش Skill Engine).
- **پیاده‌سازی (`src/automa/roles/`):** هر نقش یک فایل TOML ‏`<name>.toml` در `src/automa/roles/builtin/` (همراه پکیج نصب می‌شه): `name` (برابر نام فایل، همون الگوی `Task.role`)، `description`، `tier` (پیش‌فرض `medium`؛ هیچ‌وقت نام مدل)، `tools`، `max_risk` (پیش‌فرض `read`؛ `external` رد می‌شه)، `max_steps` (۱ تا ۲۰۰، سقف قدم Worker)، `instructions` (پرامپت سیستمی). مدل `Role` تغییرناپذیر و `extra="forbid"`ه و `Role.policy()` یک `PermissionPolicy` می‌سازه — این Policy اجرا می‌شه، نه متن پرامپت. `RoleRegistry.from_dir`/`builtin` بارگذاری رو بسته شکست می‌ده: فایل خراب، symlink، غیرمعمولی (مثل FIFO، بدون قفل شدن)، بزرگ‌تر از ۶۴KiB، غیر UTF-8، نام ناهمخوان یا نقش تکراری کل مجموعه رو رد می‌کنه؛ با دادن ابزارها، ابزار ناشناخته یا ابزاری بالاتر از `max_risk` نقش هم خطاست (ابزار `external` مجازه ولی همیشه Approval می‌خواد). نقش‌های داخلی: `researcher`، `architect`، `writer` (فقط خوندن/نوشتن فایل، سطح `write`) و `developer` (به‌علاوه `run_command`، سطح `execute`). `automa new` نام نقش‌ها رو به‌عنوان `known_roles` به Executive می‌ده، پس برنامه با نقش ناشناخته رد و تکرار می‌شه (جزئیات: D19).
- **`WorkerAgent` (`src/automa/agents/worker.py`):** فقط با `LLMGateway` ساخته می‌شه. `run(task, role, executor, project_id=…, attempt=…, feedback=…, tier=…)` یک تلاش رو اجرا می‌کنه و `TaskResult` برمی‌گردونه. پیام سیستمی = `instructions` نقش + قرارداد کار؛ پیام کاربر = `task_message` (عنوان، توضیح، ورودی‌ها، معیارهای پذیرش با شماره و بررسی قطعی، و ایرادهای Verifier در تلاش بعدی). هر قدم یک فراخوانی مدل با specهای ابزارهای مجاز؛ tool callها فقط از `ToolExecutor` اجرا می‌شن؛ پاسخ بدون ابزار = پایان (`completed`)؛ سقف `min(role.max_steps, settings.max_steps)` ← `step_limit`؛ `content_filter` ← `failed`. Policy Executor باید دقیقاً `role.policy()` باشه. خطاهای بودجه/Provider، `ApprovalRequired` و `ToolLayerError` بالا می‌رن و تکرار نمی‌شن. رویدادهای `worker.started`/`worker.step`/`worker.finished` بدون محتوا. ذخیره نتیجه در `tasks/<id>/` با Orchestratorه (جزئیات: D20).

### Verifier Agent
- مستقل از Worker: پیام‌ها و استدلال Worker رو نمی‌بینه، فقط خروجی و معیار پذیرش رو.
- اول **بررسی‌های قطعی** اجرا می‌شن (تست‌ها، وجود فایل‌ها، اجرای دستورها). فقط اگر قبول شدن، ارزیابی مدلی انجام می‌شه.
- خروجی: `pass` یا `fail` + فهرست ایرادها که به Worker برمی‌گرده.
- **پیاده‌سازی (`src/automa/agents/verifier.py`):** `VerifierAgent` فقط با `LLMGateway` ساخته می‌شه. `verify(task, result, executor, project_id=…, tier=…)` یک `Verdict` برمی‌گردونه. Executor باید Policy **دقیقاً** `verifier_policy()` داشته باشه (`read_file`، `list_dir`، `run_command`؛ سقف `execute`؛ بدون `write_file`). ترتیب: (۱) نتیجه غیر `completed` ← `fail` فوری بدون بررسی و بدون مدل؛ (۲) `run_checks` همه بررسی‌های قطعی رو از `ToolExecutor` اجرا می‌کنه: `file_exists` (فایل با `read_file` یا پوشه با `list_dir`)، `file_contains` (نشانه بریدن `read_file` هیچ‌وقت متن مورد انتظار حساب نمی‌شه)، `command` (`shlex.split` بدون shell ← `run_command` با `timeout_s` بررسی و مقایسه `exit_code`)؛ هر بررسی ناموفق یک `Issue` با شماره معیار می‌سازه؛ (۳) فقط اگه همه قبول شدن و معیاری بدون بررسی وجود داشت، ارزیابی مدلی: پیام فقط شامل وظیفه، معیارها و محتوای فایل‌ها (فایل‌های `result.files` + مسیر بررسی‌ها، با سقف تعداد/اندازه) — **نه** خلاصه یا گفت‌وگوی Worker، و بدون ابزار. پاسخ باید برای **هر** معیار خواسته‌شده دقیقاً یک قضاوت (`passed` بولی سخت‌گیرانه + دلیل برای رد) بده؛ پاسخ نامعتبر/بریده/فیلترشده با بازخورد تکرار می‌شه (پیش‌فرض ۲ بار) وگرنه `VerificationFailed` — هیچ‌وقت `pass`. خطاهای بودجه/Provider و `ToolLayerError` بالا می‌رن. رویدادهای `verifier.checks`/`verifier.reply_rejected`/`verifier.verdict` بدون محتوا (جزئیات: D21).

### LLMGateway
- یک کلاینت سازگار با OpenAI Chat Completions. `base_url`، `api_key` و نام مدل‌ها از تنظیمات میاد؛ پس هر درگاهی (OpenRouter، درگاه‌های داخلی، یا ارائه‌دهنده مستقیم) با تغییر تنظیمات قابل استفاده‌ست.
- **سطح‌ها (tiers):** `small`، `medium`، `large`. نقش‌ها سطح می‌خوان، نه نام مدل. نگاشت سطح به مدل در تنظیماته.
- **ارتقای سطح:** اگر وظیفه‌ای با یک سطح دو بار رد شد، با سطح بالاتر تکرار می‌شه.
- هر فراخوانی، قبل از ارسال از Budget Guard اجازه می‌گیره و بعدش در Ledger ثبت می‌شه؛ Guard اجباریه و اگه Provider خطا بده رزرو آزاد می‌شه.
- یک **ارائه‌دهنده ساختگی (FakeProvider)** برای تست‌ها، تا توسعه و آزمون بدون هزینه انجام بشه.
- **تلاش دوباره (`[provider]`):** خطاهای موقت درگاه (timeout، شبکه، 429، 5xx) تا `max_retries` بار دوباره امتحان می‌شن؛ هر تلاش در `_attempt` جدا از Guard اجازه می‌گیره. درخواستی که فرستاده شده ولی جوابش نیومده با بدترین هزینه ثبت می‌شه. 402 و 401 تکرار نمی‌شن. پیام خطای درگاه (بدون کلید) به کاربر می‌رسه (D91).
- **پیاده‌سازی (`src/automa/llm/`):** `types.py` (انواع داده)، `provider.py` (رابط `Provider` و `ProviderError`)، `openai_compat.py`، `fake.py`، `gateway.py`. هر فراخوانی `max_tokens` اجباری داره؛ Gateway قبل از ارسال یک `CallEstimate` (بدترین هزینه ممکن) به `CallGuard.authorize` می‌ده و بعد از پاسخ `CallGuard.record` رو با هزینه واقعی صدا می‌زنه. هزینه واقعی هیچ‌وقت کمتر از محاسبه با قیمت مدل درخواستی نیست (جزئیات: D8). Gateway در سازنده هر Guard بدون `authorize`/`record`/`release` قابل فراخوانی رو رد می‌کنه؛ usage با توکن صفر همیشه با بدترین حالت حساب می‌شه؛ خطا بعد از پاسخ Provider با ثبت بدترین حالت همراهه. `tests/test_guard_bypass.py` با بررسی AST تضمین می‌کنه فقط `LLMGateway._attempt` (بعد از `authorize`) Provider رو صدا بزنه و `complete` فقط از طریق `_attempt` (جزئیات: D12، D91).

### Budget Guard و Cost Ledger (لایه مالی)
- **Ledger:** هر فراخوانی با زمان، پروژه، وظیفه، مدل، توکن ورودی/خروجی و هزینه در SQLite ثبت می‌شه.
  **پیاده‌سازی (`src/automa/budget/ledger.py`):** `CostLedger` در `<workspace>/ledger.sqlite3`؛ پول به‌صورت nano-USD صحیح با گرد کردن رو به بالا، روزها UTC، نسخه schema در `user_version` (جزئیات: D9).
- **سقف‌ها:** سقف هر پروژه، سقف روزانه و سقف هر فراخوانی. رسیدن به سقف = توقف قطعی و درخواست تأیید از کاربر. این قانون در کده و Agentها نمی‌تونن تغییرش بدن.
  **پیاده‌سازی (`src/automa/budget/guard.py`):** `BudgetGuard` تنها `CallGuard` تولیدیه و `LLMGateway` بدون Guard ساخته نمی‌شه. `authorize` بدترین هزینه رو رزرو می‌کنه (خرج Ledger + رزروها + درخواست ≤ سقف)، `record` هزینه واقعی رو ثبت و رزرو رو آزاد می‌کنه، `release` رزرو فراخوانی ناموفق رو آزاد می‌کنه. رسیدن به سقف روزانه/پروژه دامنه رو latch می‌کنه و خطای `BudgetExceeded` می‌ده (جزئیات: D10).
- **هشدار:** در ۵۰٪ و ۸۰٪ سقف به کاربر گزارش می‌شه.
  **پیاده‌سازی:** `BudgetGuard` بعد از هر `record`، وقتی خرج واقعی برای اولین بار به ۵۰٪ و ۸۰٪ سقف روزانه یا پروژه می‌رسه، رویداد `budget.warning` و برای هر توقف قطعی جدید رویداد `budget.stop` می‌سازه (یک بار برای هر دامنه/کلید/آستانه). رویدادها همیشه در حافظه Guard می‌مونن و اگه `EventSink` داده شده باشه (مثلاً `JsonlEventLog` روی `events.jsonl`) به اون هم فرستاده می‌شن. خطای Sink نه ثبت Ledger رو برمی‌گردونه نه latch رو، ولی به‌صورت `BudgetError` بالا میاد (جزئیات: D11).
- قیمت مدل‌ها از تنظیمات یا پاسخ درگاه (اگر هزینه رو برگردونه) خونده می‌شه.
- **کاتالوگ مدل (D94):** بخش اختیاری `[models."<id>"]` در `automa.toml` برای هر مدل `family` (سازنده، مثلاً `anthropic`)، `capabilities` (`text`، `code`، `vision`، `image_out`) و قیمت (`input_per_mtok`، `output_per_mtok`) داره. `AutomaConfig.price_for` قیمت رو از `[prices]` یا کاتالوگ می‌خونه؛ هر مدل سطح‌ها باید در یکی‌شون باشه، یک مدل در هر دو جا خطاست، و مدل سطح در کاتالوگ باید `text` داشته باشه. خانواده و توانایی فقط داده‌ان برای انتخاب مدل (ارزیاب از خانواده دیگر، مدل هر نقش) و هیچ ابزار، سطح ریسک یا بودجه‌ای نمی‌دن.
- **فرمان `automa models` (D95):** فهرست فقط‌خواندنی کاتالوگ (فیلتر `--capability`/`--family`، خروجی `--json`، سطح‌هایی که هر مدل رو استفاده می‌کنن). `automa models import --format 1xai FILE --rate R` با ماژول خالص `automa.model_import` فهرست قیمت متنی درگاه (تومان به ازای ۱K توکن) رو با حساب دهدهی دقیق به دلار به ازای ۱M توکن تبدیل و **رو به بالا** گرد می‌کنه، خانواده و توانایی رو از پیشوند شناسه حدس می‌زنه (علامت‌گذاری‌شده برای بازبینی) و فقط چاپ می‌کنه؛ خروجی قبل از چاپ دوباره parse و اعتبارسنجی می‌شه و `automa.toml` هرگز نوشته نمی‌شه.
- **ارزیاب از خانواده دیگر (D96):** بخش اختیاری `[verifier]` با `prefer_other_family` (پیش‌فرض خاموش) و `models` (حداکثر ۲۰، بدون تکرار، همه در کاتالوگ با توانایی `text`؛ روشن بدون فهرست ← خطای تنظیمات). `choose_evaluator(config, worker_model)` در `agents/verifier.py` تابعی خالصه: اولین مدل فهرست (به ترتیب صاحب مخزن) که خانواده‌اش با خانوادهٔ مدل Worker (`result.model`) فرق داره؛ اگه خانوادهٔ Worker نامعلوم بود (`worker_family_unknown`) یا مدلی از خانوادهٔ دیگه نبود (`no_other_family`) همون مدل سطح Verifier مثل قبل. `VerifierAgent` فقط برای ارزیابی مدلی این انتخاب رو اعمال می‌کنه (بررسی‌های قطعی دست نخوردن)، با رویداد `verifier.evaluator` (مدل، خانواده، مدل/خانوادهٔ Worker، دلیل، `fallback`). `LLMGateway.complete(..., model=…)` مدل مشخص رو می‌پذیره (`check_model`: قیمت لازم، و اگه در کاتالوگه `text`؛ وگرنه `ConfigError` قبل از هر مجوز یا ارسال) و همون مسیر Guard/Ledger رو طی می‌کنه؛ سطح هم ثبت می‌شه. هیچ‌وقت به مدل ارزون‌تر برنمی‌گرده: رد Guard بالا می‌ره. `Verdict` فیلدهای اختیاری `evaluator_model`/`evaluator_family` (فقط وقتی `model_evaluated`) داره و `QualityRecord`/`QualityLog` (نسخهٔ طرح ۲) ستون‌های `verifier_model`/`verifier_family`؛ لاگ نسخهٔ ۱ در باز شدن نوشتنی با `ALTER TABLE` مهاجرت می‌کنه و در باز شدن فقط‌خواندنی بدون تغییر خونده می‌شه (ستون‌ها `None`)؛ ستون‌های ناشناخته ← بسته شکست.
- **مدل هر نقش، قانون‌محور (D97):** `[roles.<name>]` علاوه بر `skills` کلیدهای `models` (نردبان مدل نقش، ضعیف‌ترین اول، حداکثر ۱۰، بدون تکرار) و `capabilities` (توانایی‌های لازم؛ فقط همراه `models`) رو می‌پذیره؛ هر مدل باید در کاتالوگ باشه و `text` و همهٔ توانایی‌های لازم رو داشته باشه. `AutomaConfig.model_for_role(role, tier)` خالص و قطعیه: بدون فهرست = `model_for(tier)`؛ با فهرست، سطح باید همچنان پیکربندی‌شده باشه و جایگاهش بین سطح‌های پیکربندی‌شده (پایین‌ترین اول) عضو فهرست رو انتخاب می‌کنه (سطح‌های بالاتر از طول فهرست ← آخرین عضو)، پس ارتقای سطح هیچ‌وقت مدل ضعیف‌تری نمی‌ده. Orchestrator برای هر تلاش مدل رو حساب می‌کنه، به `WorkerAgent.run(..., model=…)` می‌ده (که با `gateway.check_model` قبل از هر فراخوانی بررسی و هر گام رو با `complete(model=…)` از همون Guard/Ledger می‌فرسته) و در `TaskState.model` (اختیاری؛ فقط برای نمایش، هر تلاش دوباره از تنظیمات حساب می‌شه) و رویدادهای `orchestrator.attempt` (`model`، `model_source: role`) و `worker.started` ثبت می‌کنه. سطح مثل قبل در وضعیت ذخیره می‌شه و ارتقا می‌یابه. Router (D58/D59) برای نقشی که فهرست مدل داره روی شواهد **مدل‌های خود نقش** کار می‌کنه (D98): شواهد هر سطح آمار (نقش، `model_for_role(role, tier)`) با قیمت کاتالوگه، پس ارزان‌ترین مدل نردبان که `min_attempts` و `min_pass_rate` رو داره (به شکل سطحی که اجراش می‌کنه) انتخاب می‌شه، وگرنه مدل پیش‌فرض نقش؛ مدل بیرون از نردبان هرگز انتخاب نمی‌شه و قاعدهٔ «هرگز گران‌تر بدون اثبات ضعف» همونه. رویداد `router.decision` برای این نقش‌ها `source: role` داره؛ `automa quality route` مدل هر سطح، میانگین هزینهٔ هر تلاش و `[role models]` رو نشون می‌ده؛ `estimate_plan` هم همین مسیر رو می‌ره. `[roles.<name>] models` برای نقشی که در Registry نیست ← `ConfigError` در ساخت Orchestrator.
- **ثبت کیفیت (`src/automa/quality.py`، D56):** `QualityLog` در `<workspace>/quality.sqlite3` (جدا از Ledger؛ جزو لایه مالی یا Policy نیست و هیچ چیزی را مجاز/مسدود نمی‌کند). یک ردیف برای هر تلاش داوری‌شده `(پروژه، وظیفه، تلاش)`: نقش (نوع وظیفه)، سطح و مدل Worker، وضعیت نتیجه، حکم Verifier، `model_evaluated`، هزینه Worker. `Orchestrator(quality=…)` بعد از هر `save_verdict` ثبت می‌کند (خطا ← فقط رویداد `quality.record_failed`)؛ `sync_project` از فایل‌های `ProjectStore` دوباره وارد می‌کند (idempotent). `stats` آمار هر (نقش، مدل) را برای Router می‌دهد. `automa run` و `bench run` لاگ را قبل از هر فراخوانی مدل باز می‌کنند (خراب ← کد ۲).
- **Router داده‌محور (`src/automa/router.py`، D58):** `Router(config, stats)` / `Router.from_log(config, log)` خالص است (بدون فراخوانی مدل، بدون نوشتن). `route(role, requested_tier)` بین سطح‌های پیکربندی‌شده، با آمار (نقش، مدل) هر سطح، ارزان‌ترین سطح واجد شرایط (حداقل `min_attempts` تلاش و نرخ قبولی ≥ `min_pass_rate`) را برمی‌گرداند؛ گران‌تر از سطح درخواستی فقط اگر سطح درخواستی با داده ضعیف ثابت‌شده باشد؛ تساوی به نفع سطح درخواستی. خروجی `RouteDecision` (سطح، مدل، دلیل `requested`/`cheaper`/`replaced`، شواهد هر سطح). تنظیمات `[router]` (`enabled` پیش‌فرض خاموش). Router فقط سطح شروع را عوض می‌کند؛ Gateway/BudgetGuard و ارتقای سطح Orchestrator بدون تغییرند. اتصال به Orchestrator (D59): `Orchestrator(router=…)` فقط برای وظیفه‌ای که هنوز نه تلاشی دارد نه سطح ذخیره‌شده، `route(task.role, task.tier or role.tier)` را صدا می‌زند، رویداد `router.decision` (وظیفه، نقش، سطح درخواستی/انتخابی، مدل، دلیل، تلاش و قبولی سطح انتخابی) می‌سازد و سطح را مثل هر سطح دیگر در `TaskState.tier` ذخیره می‌کند؛ پس ادامه اجرا دوباره مسیریابی نمی‌کند و ارتقای سطح از سطح انتخابی ادامه می‌یابد. Router باید از همان `AutomaConfig` Orchestrator ساخته شده باشد (وگرنه `ValueError`)؛ سطح درخواستی پیکربندی‌نشده ← توقف `config` قبل از هر فراخوانی مدل. Orchestrator خودش `enabled` را بررسی نمی‌کند (کار CLI). در `automa run` (D60): `--router`/`--no-router` بر `[router] enabled` مقدم است؛ Router بعد از باز کردن لاگ کیفیت و قبل از هر فراخوانی مدل از snapshot آمار ساخته می‌شود (آمار خراب ← کد ۲)، و خط `router:` وضعیت و آستانه‌ها را نشان می‌دهد. `bench run` هرگز مسیریابی نمی‌کند تا مقایسه پیکربندی‌ها ثابت بماند. پیش‌نمایش (D61): `automa quality route` لاگ کیفیت را فقط‌خواندنی (`mode=ro`) باز می‌کند، با همان `Router` و تنظیمات `[router]` (حتی وقتی `enabled` خاموش است) برای هر نقش داخلی و هر نقش موجود در آمار، سطح انتخابی، دلیل و شواهد همه سطح‌ها را نشان می‌دهد؛ سطح درخواستی = `--tier` یا سطح پیش‌فرض نقش (سطح وظیفه در پلن پروژه‌ها را نمی‌بیند). بدون کلید، بدون Provider و بدون نوشتن.
- **ثبت کیفیت در CLI (`cli.py`، D57):** `automa quality [--role R] [--json]` آمار `stats` را به‌صورت جدول (نقش، مدل، سطح‌ها، تلاش، قبولی، نرخ، هزینه کل/میانگین/به‌ازای هر قبولی) نشان می‌دهد؛ لاگ را با `QualityLog(read_only=True)` (SQLite با `mode=ro`، بدون ساخت/مهاجرت/نوشتن) باز می‌کند و لاگ ناموجود یعنی خالی (هیچ فایلی ساخته نمی‌شود)؛ لاگ خراب ← کد ۲. `automa quality sync [<id>] [--json]` با `sync_project` تلاش‌های داوری‌شده یک یا همه پروژه‌ها را وارد می‌کند (idempotent)؛ پروژه ناموجود ← کد ۱ بدون ساخت لاگ، لاگ غیرقابل‌باز ← کد ۲، شکست یک پروژه گزارش می‌شود و بقیه وارد می‌شوند (کد ۱). `record` در رقابت دو پروسه (IntegrityError) ردیف یکسان را no-op و ردیف متفاوت را تعارض می‌داند. هیچ‌کدام کلید API یا Provider نمی‌خواهند.

### Tool Layer و Permission Policy
- ابزارها کلاس‌های ساده با نام، توضیح، پارامترها و **سطح ریسک**ان: `read`، `write`، `execute`، `external` (شبکه/انتشار/پرداخت).
- هر نقش فهرست ابزارهای مجازش رو داره.
- ابزارهای `write` و `execute` فقط داخل پوشه کاری پروژه کار می‌کنن.
- ابزارهای سطح `external` و هر اقدام برگشت‌ناپذیر از **Approval Gate** رد می‌شن: پروژه متوقف می‌شه تا کاربر تأیید کنه.
- اجرای کد می‌تونه داخل کانتینر Docker ایزوله انجام بشه (`RunCommand(sandbox=DockerSandbox(...))`)؛ انتخاب با بخش `[sandbox]` در `automa.toml` (پایین‌تر).

- **پیکربندی Sandbox (`config.py`، D33):** `[sandbox]` با `mode = "local"|"docker"` (پیش‌فرض `local`) و در حالت `docker` گزینه‌های `image`/`docker`/`memory_mb`/`cpus`/`pids_limit` (همون اعتبارسنجی `DockerSandbox`، هنگام بارگذاری تنظیمات). گزینه Docker با `mode = "local"` رد می‌شه (توهم ایزوله‌سازی) و کلید ناشناخته (مثل `network`/`privileged`) هم. `SandboxConfig.docker_sandbox()` ← `DockerSandbox | None`. `default_tools(sandbox)` و `tools_factory(sandbox)` ابزارها رو با همون sandbox می‌سازن. - **`fetch_url` (`tools/web.py`، سطح `external`، D72):** خواندن یک صفحهٔ وب عمومی به‌صورت متن با `httpx` (در تست `MockTransport` و resolver جعلی). چون `external` است هر فراخوانی از Approval Gate می‌گذرد و تأیید فقط برای همان نشانی دقیق است؛ فقط نقش داخلی `researcher` آن را در فهرست دارد (D73؛ `max_risk` همان `write`، پس قانون ۳ Policy هر فراخوانی را `needs_approval` می‌کند). محافظ‌های خود ابزار (حتی بعد از تأیید): فقط `http`/`https`، بدون userinfo، حداکثر ۲۰۴۸ نویسه، بدون فاصله/کاراکتر کنترلی (در اعتبارسنجی آرگومان، پس نشانی نامعتبر به Gate نمی‌رسد)؛ همهٔ نشانی‌هایی که میزبان به آن resolve می‌شود باید `is_global` و غیر multicast باشند (IPv4-mapped هم بررسی می‌شود)؛ redirect دستی حداکثر ۳ بار و هر بار همین بررسی‌ها؛ `trust_env=False` (بدون proxy محیط، `.netrc` و کوکی)؛ timeout پیش‌فرض ۱۵ ثانیه؛ بدنه تا ۱MiB؛ فقط `text/*` و چند نوع JSON/XML؛ HTML با `HTMLParser` به متن (بدون `script`/`style`/`head`/…)؛ خروجی با سرتیتر ثابت «داده نه دستور» و URL/وضعیت/نوع/عنوان، بریده به `max_chars`. `audit()` فقط نام میزبان را در `tool.call` ثبت می‌کند (query ممکن است توکن داشته باشد). ریسک باقی‌مانده: DNS rebinding بین بررسی و اتصال. نمای خوانا (D73): `describe_fetch_request` خالص (بدون resolve و شبکه) طرح، میزبان به شکل ارسالی (IDNA/punycode)، درگاه، مسیر و هشدارها (http رمزنشده، میزبان IP، میزبان غیر ASCII یا `xn--`، درگاه غیرپیش‌فرض، query string که به میزبان فرستاده می‌شود، مسیر خیلی بلند) را می‌دهد؛ `automa approvals` و `automa approve` (قبل از پرسش تأیید) بخش «web request:» را بالای آرگومان‌های دقیق نشان می‌دهند و `--json` کلید `web_request` دارد.

در مجوز Guard، بررسی `[images]` در برابر `per_call_usd`، `image_price()`/برآورد و خط `images:` به کار می‌رود. هزینهٔ ثبت‌شده: توکن‌های گزارش‌شده به قیمت کاتالوگ (بدون توکن خروجی ← بدترین حالت؛ ورودی - **Approval Gate (`tools/approvals.py`):** ابزار `external` فقط اگه در `allowed_tools` نقش باشه `needs_approval` می‌گیره (وگرنه `deny`). `ToolExecutor` با `approvals=ApprovalStore` و `task_id` (Orchestrator فقط برای Worker می‌ده) اول آرگومان‌ها رو اعتبارسنجی می‌کنه، بعد دنبال تصمیم مصرف‌نشده برای دقیقاً همین وظیفه + ابزار + اثرانگشت SHA-256 آرگومان‌های canonical می‌گرده: تأیید ← مصرف با فایل نشانه `<id>.used` (`O_EXCL`، حداکثر یک بار) و بعد اجرا (`tool.approved`)؛ رد ← نتیجه ناموفق با یادداشت کاربر به مدل (`tool.rejected`)؛ هیچ ← ثبت `ApprovalRequest` (`pending`، یا استفاده دوباره از درخواست در انتظار یکسان) در `projects/<id>/approvals/<apr-id>.json` و `ApprovalRequired(request_id=…)` ← پروژه `paused` و `RunReport.approval_id`. `ApprovalStore.decide` فقط یک بار روی `pending`. Executor بدون Store هیچ‌وقت چیزی رو قابل تأیید نمی‌کنه. خطای Store ← `ToolLayerError` (جزئیات: D29).
- **Approval Gate (اقدامات برگشت‌ناپذیر):** هر `Tool` یک `irreversible: ClassVar[bool]` (پیش‌فرض `False`، فقط bool واقعی) داره. `PermissionPolicy.decide(name, risk, irreversible=…)` اول قانون‌های فهرست و سقف ریسک رو اعمال می‌کنه (رد همون رده و تأیید نمی‌تونه برش داره) و بعد ابزار برگشت‌ناپذیر رو در هر `max_risk` ← `needs_approval` می‌کنه؛ بقیه مسیر دقیقاً همون Approval Gate ابزار `external`ه (درخواست، تصمیم یک‌باره، مصرف حداکثر یک بار). رویدادهای Gate برای این ابزارها `irreversible: true` دارن. `specs()` ابزارهای `needs_approval` رو فقط وقتی Executor Store تأیید داره به مدل نشون می‌ده (بدون Store هیچ‌وقت قابل اجرا نیستن). اولین ابزار برگشت‌ناپذیر `delete_file` (سطح `write`؛ `Workspace.delete_file` فقط فایل معمولی، نه پوشه یا symlink، بدون دنبال کردن symlink در مسیر) که مسیرش قبل از ثبت درخواست اعتبارسنجی و نرمال می‌شه؛ به هیچ نقش داخلی داده نشده (جزئیات: D31).
- **Approval Gate (CLI، `cli.py`):** `automa approvals [<project>] [--all] [--json]` (فقط‌خوندنی، بدون کلید) درخواست‌ها رو با وظیفه، ابزار، ریسک، دلیل، وضعیت (`used` برای تصمیم مصرف‌شده) و آرگومان‌های دقیق نشون می‌ده (پیش‌نمایش ۲۰۰۰ نویسه + مسیر فایل). `automa approve <project> <id> [--note] [--yes]` اول کل درخواست رو با آرگومان‌های کامل نشون می‌ده و تأیید صریح می‌خواد (پیش‌فرض «نه»)؛ `automa reject` بدون پرسش. هر دو فقط `ApprovalStore.decide` رو صدا می‌زنن (یک بار، فقط `pending`، فقط درخواست همون پروژه) و رویداد `approval.decided` (بدون متن یادداشت) ثبت می‌کنن؛ اجرای خود ابزار فقط در `automa run` بعدی. همه متن‌های ضبط‌شده قبل از چاپ از `_safe` رد می‌شن (escape نویسه‌های کنترلی/قالب مثل ANSI، `\r`، C1 و جهت‌دهی bidi؛ ZWNJ/ZWJ مجاز). `automa status` درخواست‌های در انتظار رو نشون می‌ده (`pending_approvals` در JSON) و `automa run` در توقف `approval` شناسه و دستورهای تصمیم رو چاپ می‌کنه (جزئیات: D30).

### Project Store
```
workspace/projects/<project-id>/
  project.json      هدف، وضعیت، بودجه، تنظیمات
  plan.json         وظایف و وابستگی‌ها
  clarifications.json  سؤال‌های Executive و پاسخ کاربر (یک بار نوشته می‌شه)
  approvals/        درخواست‌های Approval Gate و تصمیم کاربر (`<id>.json` + نشانه مصرف `<id>.used`)
  tasks/<task-id>/  ورودی، خروجی، نتیجه ارزیابی، تاریخچه تلاش‌ها
  files/            خروجی‌های واقعی پروژه (کد، سند، …)
  events.jsonl      لاگ همه رویدادها
workspace/workflows/<wf-id>.json   قالب‌های Workflow (برنامه پروژه‌های موفق D38، یا تعریف/ویرایش کاربر D41)
workspace/skills/<name>/SKILL.md   Skillهای کاربر (در کنار Skillهای داخلی؛ D45)
```
لاگ رویدادها با `automa.events` نوشته می‌شه: `Event` (زمان UTC، نوع نقطه‌دار مثل `budget.warning`، `project_id`، `data`)، رابط `EventSink`، `JsonlEventLog` (یک JSON در هر خط، فقط افزودنی، خط خراب هنگام خوندن خطا می‌ده) و `MemoryEventSink`.
پیاده‌سازی در `automa.project`: `ProjectStore` (ریشه `<workspace>/projects`) با `create`/`load`/`save`/`set_status`/`list_projects`. `project.json` مدل `Project` است (`schema_version`، `id`، `goal`، `status`، `created_at`، `updated_at`، `revision`) و اتمی نوشته می‌شه؛ `save` با `revision` همزمانی خوش‌بینانه داره (`ProjectConflict`). شناسه پروژه فقط `a-z0-9-` و پوشه پروژه نمی‌تونه symlink یا بیرون از ریشه باشه. `store.events(id)` یک `ProjectEventLog` برمی‌گردونه که `project_id` رویدادها رو اجباری می‌کنه و به‌عنوان `EventSink` به `BudgetGuard` داده می‌شه (جزئیات: D13). `save_plan`/`load_plan` فایل `plan.json` رو اتمی و فقط با `version` بزرگ‌تر می‌نویسن و رویداد `plan.saved` ثبت می‌کنن (D14). `save_clarifications`/`load_clarifications` فایل `clarifications.json` (مدل `Clarifications` در `automa.plan`) رو اتمی و فقط یک بار می‌نویسن (رویداد `clarifications.saved`)؛ نبود فایل یعنی فهرست خالی.
`tasks/<task-id>/` (پوشه‌ها و فایل‌ها هیچ‌وقت symlink نیستن): `result-<n>.json` (`TaskResult`) و `verdict-<n>.json` (`Verdict`) write-once و با شماره پشت‌سرهم (`save_task_result`/`save_verdict`؛ تلاش بعدی فقط بعد از Verdict قبلی؛ Verdict باید با نتیجه ذخیره‌شده و وظیفه برنامه `matches` باشه)، و `state.json` (`TaskState`: `status`، `attempts`، `tier` تلاش بعدی، `plan_version`، `error`، `revision`) با `save_task_state` که فقط وضعیت سازگار با تاریخچه رو می‌پذیره (`passed` فقط با Verdict قبولی آخرین تلاش). `task_states`/`passed_tasks` وضعیت وظایف برنامه فعلی رو می‌دن (وضعیت نسخه قدیمی برنامه ← `pending`). رویدادها: `task.result_saved`، `task.verdict_saved`، `task.status` (جزئیات: D22).
فایل‌محور بودن یعنی وضعیت قابل خوندن، قابل ادامه و قابل بررسی دستیه.

### Workflowهای ذخیره‌شده (`src/automa/workflows.py`، D38)
برنامه پروژه‌ای که با موفقیت تموم شده (وضعیت `done` و **همه** وظایف برنامه فعلی `passed`؛ Store فقط با Verdict قبولی ذخیره‌شده وظیفه رو `passed` می‌کنه) با `WorkflowStore.save_from_project(projects, project_id)` به‌عنوان قالب در `<workspace>/workflows/<id>.json` ذخیره می‌شه: `WorkflowTemplate` (`schema_version`، `id` = `wf-<زمان UTC>-<hex>`، `goal` مبدأ، `source_project`، `source_plan_version`، `created_at`، `plan` با `version` = ۱، و `stats`: تعداد وظایف، تلاش‌های Worker، مجموع `cost_nusd` نتیجه‌ها). هر فایل یک بار نوشته می‌شه (`os.link`، هیچ‌وقت بازنویسی نمی‌شه) و هر پروژه حداکثر یک بار ذخیره می‌شه؛ رویداد `workflow.saved` در `events.jsonl` پروژه مبدأ. خوندن شکست بسته‌ست: JSON خراب، فیلد اضافه، شناسه ناجور با نام فایل، برنامه نامعتبر، و symlink (فایل یا خود پوشه `workflows/`) خطای `WorkflowError` می‌دن.
`suggest(goal, limit=3, min_score=0.2)` قالب‌ها رو با شباهت Jaccard واژه‌های محتوایی هدف‌ها مرتب می‌کنه (`goal_terms`: casefold، یکسان‌سازی ی/ک عربی و فارسی، ZWNJ جداکننده، حذف stopwordهای فارسی و انگلیسی و عددها)؛ بدون فراخوانی مدل و بدون هزینه، قطعی، و در تساوی قالب جدیدتر اول. این ماژول هیچ پروژه‌ای رو تغییر نمی‌ده و هیچ قالبی رو اجرا نمی‌کنه؛ اتصال به CLI و استفاده از قالب برای پروژه جدید موردهای بعدی M6‌ان.

**CLI (D39):** `automa workflow save <project> [--json]` همون `save_from_project` رو صدا می‌زنه (بدون کلید API و بدون مدل؛ خطاها ← کد خروج ۱) و یادآوری می‌کنه که قالب کپی متن‌ها و ورودی‌های پروژه‌ست. `automa workflows [--json]` قالب‌ها رو از جدید به قدیم فهرست می‌کنه (فقط‌خوندنی، هیچ پوشه‌ای نمی‌سازه، روی فایل خراب شکست بسته با کد ۱). `automa new` بعد از اعتبارسنجی پیکربندی و ساخت پروژه و قبل از سؤال‌های Executive، تا ۳ قالب مشابه رو با درصد شباهت و واژه‌های مشترک چاپ می‌کنه — **فقط پیشنهاد**: برنامه همچنان از Executive میاد و هیچ چیزی نوشته نمی‌شه. خرابی پوشه `workflows/` فقط یک هشدار روی stderr می‌ده و جلوی پروژه جدید رو نمی‌گیره. متن هدف قالب‌ها با `_safe` (فرار کاراکترهای کنترلی) چاپ می‌شه.

**استفاده (D40):** `automa new GOAL --workflow <id>` برنامه قالب رو به‌جای Executive به پروژه جدید می‌ده: `plan_from_template(template, goal, role_tiers, configured_tiers)` نقش‌ها (در برابر نقش‌های فعلی) و سطح شروع هر وظیفه (`task.tier` یا سطح نقش؛ باید مدل پیکربندی‌شده داشته باشه) رو **قبل از ساخت پروژه** بررسی می‌کنه (ناسازگاری ← `WorkflowIncompatible`، کد ۲؛ قالب ناموجود/خراب ← کد ۱؛ هیچ پروژه‌ای ساخته نمی‌شه). بعد `WorkflowStore.use(projects, project_id, workflow_id, ...)` قالب رو دوباره می‌خونه، برنامه رو با هدف جدید و `version` = ۱ ذخیره می‌کنه، وضعیت ← `planning`، رویداد `workflow.used`؛ روی خطا وضعیت قبلی برمی‌گرده. بدون Provider، کلید، سؤال یا هزینه؛ فایل قالب تغییر نمی‌کنه و اجرای وظایف با `automa run` مثل همیشه از همه لایه‌های امنیتی و مالی می‌گذره.

**تعریف و ویرایش توسط کاربر (D41):** `WorkflowTemplate.origin` = `project` (بالا) یا `user`. `WorkflowStore.create(goal, plan, role_tiers=…, configured_tiers=…)` برنامه JSON کاربر رو با `user_plan` (همه قوانین `Plan`؛ هدف و `version` = ۱ جایگزین می‌شن) و `check_compatible` (نقش‌ها و سطح شروع، همون بررسی `plan_from_template`) اعتبارسنجی و به‌عنوان قالب `user` ذخیره می‌کنه. `WorkflowStore.revise(id, goal=…, plan=…)` قالب `user` **جدید** با `parent` = `id` می‌سازه (والد هرگز تغییر نمی‌کنه؛ ویرایش بدون تغییر رد می‌شه) و `history(id)` زنجیره والدها رو برمی‌گردونه (شکست بسته روی والد گمشده/چرخه). قالب `user` هیچ‌وقت `source_project`/`stats` نداره — آمار فقط ادعای برنامه‌ای‌ه که دقیقاً اجرا و قبول شده. استفاده (`use`) و پیشنهاد برای هر دو نوع یکسانه؛ CLI قالب `user` رو با `user-defined`/`user, edited from <id>` و `not run yet` نشون می‌ده.

**CLI تعریف/ویرایش (D42):** `automa workflow create --goal … --plan <file.json>` و `automa workflow edit <id> [--goal …] [--plan <file>]` فایل برنامه (حداکثر `MAX_PLAN_FILE_BYTES` = ۱MB، فایل معمولی، UTF-8، JSON) رو می‌خونن و `create`/`revise` رو با نقش‌های داخلی و سطح‌های پیکربندی‌شده (`_compat_context`، همون بررسی `new --workflow`) صدا می‌زنن؛ ناسازگاری ← کد ۲، بقیه خطاها ← کد ۱، و هیچ چیزی ذخیره نمی‌شه. `automa workflow show <id> [--json | --plan-json]` فقط‌خوندنیه: منبع، زمان، آمار، زنجیره ویرایش (`history`؛ والد گمشده فقط هشدار، و `history: null` در JSON)، هدف کامل و برنامه؛ `--plan-json` فقط برنامه رو بدون `goal`/`version` چاپ می‌کنه — دقیقاً فایلی که `edit --plan` می‌پذیره. هیچ‌کدوم کلید API، Provider یا فراخوانی مدل ندارن.

### حافظه
سه لایه جدا: ترجیحات کاربر، دانش اختصاصی هر پروژه، و درس‌های عمومی (مثلاً «سرویس X برای Y مناسب نبود»). درس‌ها بعد از پایان هر پروژه توسط یک مرحله «بازبینی» استخراج می‌شن (مرحله بعد؛ پیشنهاد مدل فقط با تأیید کاربر وارد حافظه می‌شه).
- **بازبینی (هسته، `src/automa/agents/reviewer.py`، D52):** `ReviewAgent.review(store, project_id, existing=…)` فقط برای پروژه `done`/`failed`. `project_digest` یک خلاصه JSON قطعی از `ProjectStore` می‌سازه (هدف ≤۸۰۰، وضعیت، هر وظیفه با وضعیت/تلاش‌ها و سه تلاش آخر: نتیجه، سطح، مدل، قدم‌ها، هزینه، خلاصه/خطای کوتاه‌شده، حکم و حداکثر ۵ ایراد Verifier)؛ سقف `MAX_DIGEST_CHARS` = ۲۴٬۰۰۰ با کاهش مرحله‌ای (بدون تاریخچه ← وظایف اول با `tasks_omitted`). خلاصه داخل `<project>` (با `<`/`>` escape‌شده) و پیام سیستمی ثابت «داده نه دستور» از مسیر `LLMGateway` (سطح پیش‌فرض `medium`) فرستاده می‌شه. پاسخ `ReviewReply`: حداکثر ۸ `Proposal` با `scope` = `project`/`lesson` (هرگز `user`) و متن ≤۱۰۰۰ نویسه با `clean_memory_text`؛ نامعتبر ← تلاش مجدد، خطای Gateway ← بدون تکرار. تکراری‌ها (درون پاسخ و نسبت به `existing`) در کد حذف می‌شن؛ `existing` به مدل نمی‌ره و `check_memory_project` حافظه پروژه دیگه رو قبل از مدل رد می‌کنه. خروجی `Review` (بدون نوشتن روی دیسک)؛ رویدادهای `review.ready` و `review.reply_rejected`. ذخیره پیشنهادها و تأیید کاربر در خط بعد؛ CLI مورد بعدیه.
- **ذخیره و تأیید بازبینی (`src/automa/reviews.py`، D53):** `ReviewStore(projects, memory)` بازبینی‌ها را در `<project>/reviews/` نگه می‌دارد: `<review_id>.json` (`StoredReview`: شناسه `rev-<تاریخ>-<hex>`، وضعیت پروژه، پیشنهادها، `created_at`/`saved_at`) و `<review_id>.d<n>.json` (`ProposalDecision`: `accepted`/`rejected`، `memory_id`، `memory_existed`) — همه با `_write_json_exclusive` یک‌بارنوشتنی. `save` فقط برای پروژه موجود `done`/`failed` که هنوز همان وضعیتِ بازبینی را دارد (سقف ۵۰ بازبینی در پروژه، پیشنهاد تکراری رد)، و هیچ حافظه‌ای نمی‌نویسد. `accept` تنها مسیر ورود پیشنهاد به حافظه است: پیشنهاد `project` در حافظه همان پروژه و `lesson` در `lessons/`، همیشه `source=review` (هرگز `user`)؛ اگر متن یکسان (نرمال‌شده) در آن لایه هست، همان ثبت می‌شود (`memory_existed`). اگر نوشتن فایل تصمیم شکست بخورد، مورد تازه‌نوشته‌شده حذف می‌شود؛ هر پیشنهاد حداکثر یک بار تصمیم می‌گیرد. `reject` فقط تصمیم را ثبت می‌کند. `all`/`latest`/`get`/`decisions`/`pending` فقط‌خواندنی‌اند و روی هر فایل خراب، بزرگ، symlink، FIFO، ناشناخته یا تصمیم بدون بازبینی شکست بسته می‌خورند. رویدادهای `review.saved`، `review.proposal_accepted`، `review.proposal_rejected` در `events.jsonl` پروژه (بدون متن پیشنهاد). مدلی صدا زده نمی‌شود؛ CLI مورد بعدی است.

- **تأیید/رد بازبینی در CLI (`cli.py`، D55):** `automa review accept|reject <id> <n>… [--review <rid>] [--yes]` (پیش‌فرض آخرین بازبینی). قبل از نوشتن هر چیزی: پروژه و بازبینی موجود و سالم، شماره‌ها در بازه، بدون تکرار و همه هنوز `pending` (یک شماره تصمیم‌گرفته = هیچ تغییری)؛ برای `accept` حافظه سالم (← کد ۲) و جای کافی در لایه‌ها برای موردهای تازه (← کد ۱). سپس متن کامل هر پیشنهاد (`_safe`) و مقصدش (حافظه همین پروژه / درس‌ها برای همه پروژه‌های آینده) نشان داده می‌شود و بدون `--yes` تأیید گرفته می‌شود (پیش‌فرض نه). تصمیم‌ها به ترتیب آرگومان‌ها با `ReviewStore.accept`/`reject`؛ شکست وسط کار شماره‌های تصمیم‌نگرفته را گزارش می‌کند (کد ۱). بدون کلید API و بدون Provider. `automa status <id>` خط `review:` (آخرین بازبینی، شمار پیشنهاد و pending، راهنمای تصمیم) و کلید JSON `review` (`count`/`latest`/`proposals`/`pending`/`error`)؛ فایل بازبینی خراب فقط گزارش می‌شود.
- **CLI (`cli.py`، D49):** `automa memory list|add|forget` روی `MemoryStore.for_workspace`. `list` سه لایه رو با متن کامل نشون می‌ده (فیلتر `--scope user|project|lesson` و `--project <id>` که فقط حافظه مرتبط با اون پروژه = کاربر + حافظه خودش + درس‌ها؛ `--json` همه فیلدها)؛ ترتیب کاربر ← پروژه ← درس، هر مورد با `_safe` فرار داده می‌شه (مورد `review` می‌تونه از مدل بیاد). `add` فقط `source=user` می‌نویسه (کاربر نمی‌تونه `review` جعل کنه)، پیش‌فرض لایه `user`؛ `--scope project` به `--project` نیاز داره و پروژه باید موجود باشه، `user` با `--project` خطاست. `forget` اول مورد رو نشون می‌ده و بدون `--yes` تأیید می‌گیره (پیش‌فرض نه). همه فقط‌خوندنی/نوشتنی محلی‌ان: بدون کلید API و بدون فراخوانی مدل؛ حافظه خراب در `list`/`add`/`forget` کد خروج ۱ و فقط در `status` گزارش می‌شه. `automa status` (فهرست و تک‌پروژه) خط `memory:` (شمار هر لایه؛ در تک‌پروژه فقط حافظه همون پروژه) و `status <id> --json` کلید `memory` (`user`/`project`/`lessons`/`error`) داره؛ اینجا حافظه خراب فرمان رو شکست نمی‌ده (D49).
- **در پرامپت‌ها (`src/automa/memory/prompt.py`، D50):** `memory_prompt(MemoryContext)` بخش `## Memory` پیام سیستمی را می‌سازد: سرتیتر ثابت (یادداشت‌ها داده‌اند نه دستور؛ وظیفه، ابزار، مجوز یا سقفی را عوض نمی‌کنند؛ در تعارض، وظیفه و قوانین برنده‌اند) و بلوک `<memory>` که هر مورد در آن یک خط JSON است (`kind` = `user_preference`/`project`/`lesson`، `text`؛ `<`/`>` و خط جدید escape می‌شوند، پس هیچ متنی نمی‌تواند تیتر یا خط تازه بسازد یا بلوک را ببندد). سقف کل `MAX_MEMORY_PROMPT_CHARS` = ۱۲٬۰۰۰ نویسه؛ انتخاب قطعی: کاربر ← پروژه ← درس، در هر لایه جدیدتر اول، مورد جاناشده رد و شمرده می‌شود (`{"omitted": n}`). `ExecutiveAgent(memory=…)` آن را به انتهای پیام سیستمی پرسش‌ها و برنامه‌ریزی، و `WorkerAgent(memory=…)` بین Skillها و `WORKER_PROTOCOL` می‌گذارد؛ پیام کاربر (هدف/وظیفه) حافظه ندارد. `check_memory_project` قبل از هر فراخوانی مدل حافظهٔ پروژهٔ دیگر یا مورد در لایهٔ اشتباه را رد می‌کند. بدون حافظه پیام سیستمی دقیقاً همان قبلی است. ابزارهای ارسالی، `Role.policy()` و BudgetGuard دست نمی‌خورند. اتصال در CLI در خط بعد.
- **در CLI (`cli.py`، D51):** `automa new` و `automa run` حافظه را قبل از هر فراخوانی مدل (و در `new` قبل از ساخت پروژه) با `MemoryStore.context` بارگذاری می‌کنند: `run` = کاربر + حافظهٔ همین پروژه + درس‌ها (به Worker؛ Verifier هرگز)، `new` = کاربر + درس‌ها (به Executive؛ پروژهٔ تازه حافظهٔ پروژه ندارد و حافظهٔ باقی‌مانده از شناسهٔ تکراری استفاده نمی‌شود). حافظهٔ خراب (JSON خراب، symlink، فایل ناشناخته) = خطای پیکربندی (کد ۲) بدون فراخوانی مدل و بدون ساخت پروژه. خاموش کردن: `--no-memory` برای یک فرمان یا `[memory] in_prompts = false` در `automa.toml` (`MemoryConfig`، `StrictBool`، کلید دیگری پذیرفته نمی‌شود)؛ `--memory` تنظیم را برای یک فرمان روشن می‌کند. هر دو فرمان خط `memory: off|on (empty)|on (n user, n project, n lessons …)` چاپ می‌کنند. `new --workflow` و `bench run` حافظه را نمی‌خوانند (benchmark باید مستقل از حافظهٔ کاربر قابل مقایسه بماند).
- **پیاده‌سازی (هسته، `src/automa/memory/`، D48):** فقط ذخیره‌سازی، بدون مدل و بدون ابزار. `MemoryEntry` (تغییرناپذیر، `extra="forbid"`): `id` (`mem-YYYYmmdd-HHMMSS-<6hex>`)، `scope` (`user`/`project`/`lesson`)، `text` (NFC، ≤۲۰۰۰ نویسه، بدون کاراکتر کنترلی جز `\n`/`\t`)، `project_id` (لازم برای `project`، ممنوع برای `user`، اختیاری برای `lesson`)، `source` (`user`/`review`؛ لایه `user` فقط `user`)، `created_at` (UTC). `MemoryStore.for_workspace(ws)` روی `<workspace>/memory/`: `user/`، `lessons/`، `projects/<project_id>/`، هر مورد `<id>.json` یک‌بارنوشتنی. `add` (تکراری نرمال‌شده در لایه و بیش از `MAX_ENTRIES_PER_LAYER` = ۲۰۰ خطا؛ ورودی نامعتبر هیچ پوشه‌ای نمی‌سازه)، `entries(scope, project_id)` (قدیمی به جدید)، `context(project_id)` ← `MemoryContext(user, project, lessons)`، `find`، `forget` (حذف فایل)، `project_ids`. بسته شکست می‌خوره: symlink در هر سطح پوشه یا فایل، فایل غیرمعمولی (FIFO بدون قفل)، بزرگ‌تر از ۱۶KiB، JSON/UTF-8 خراب، شناسه ناهمخوان، مورد در لایه/پروژه اشتباه یا ورودی ناشناخته کل لایه رو رد می‌کنه (فایل‌های مخفی موقت نادیده گرفته می‌شن). CLI، استفاده در پرامپت‌ها و مرحله بازبینی موردهای بعدی‌ان.

### Skill Engine
Skillها با قالب استاندارد `SKILL.md` (frontmatter + دستورالعمل) در `skills/` نگهداری می‌شن. انتخاب Skill بر اساس توضیحش انجام می‌شه. ساخت خودکار Skill آخرین مرحله‌ست و فقط بعد از اینکه مجموعه آزمون ارزیابی قوی شد فعال می‌شه؛ هر Skill جدید قبل از ورود باید روی آزمون‌ها بهتر یا مساوی عمل کنه.
- **پیاده‌سازی (هسته، `src/automa/skills/`):** هر Skill یک پوشه `<name>/` با فایل `SKILL.md`ه. `split_frontmatter` یک زیرمجموعه کوچک و قطعی از YAML رو بدون وابستگی جدید می‌خونه: خط اول `---`، هر خط یک `key: value` (ساده یا داخل `'…'`/`"…"` بدون escape)، کامنت و خط خالی مجاز، بدون تودرتو/فهرست/مقدار چندخطی، و بسته شدن با `---`؛ هر چیز خارج از این زیرمجموعه خطاست نه حدس. فیلدها فقط `name` (الگوی `^[a-z0-9](?:[a-z0-9-]{0,62}[a-z0-9])?$` بدون `--`، برابر نام پوشه)، `description` (یک‌خطی، حداکثر ۱۰۲۴) و `license` اختیاری‌ان؛ بدنه Markdown (غیرخالی، حداکثر ۲۰٬۰۰۰ نویسه) دستورالعمله. `allowed-tools`/`tools` عمداً رد می‌شه: Skill فقط متن به پرامپت اضافه می‌کنه و هیچ ابزار، سطح ریسک یا بودجه‌ای نمی‌ده — این‌ها فقط از `Role.policy()` و `BudgetGuard` میان. `SkillRegistry.from_dir` مثل `RoleRegistry` بسته شکست می‌خوره: پوشه symlink، ورودی symlink، `SKILL.md` گمشده/symlink (`O_NOFOLLOW`)/غیرمعمولی (FIFO بدون قفل)/بزرگ‌تر از ۶۴KiB/غیر UTF-8، نام ناهمخوان یا تکراری کل مجموعه رو رد می‌کنه؛ ورودی‌های مخفی و فایل‌های ساده سطح بالا (مثل README) نادیده گرفته می‌شن. `from_optional_dir` پوشه ناموجود رو مجموعه خالی می‌دونه (ولی symlink رو نه). اتصال به نقش‌ها و CLI مرحله بعده (جزئیات: D43).
- **اتصال به نقش‌ها:** فیلد اختیاری `Role.skills` (حداکثر ۸ نام، بدون تکرار). `RoleRegistry(..., skills=SkillRegistry)` وجود Skillها رو موقع بارگذاری بررسی می‌کنه. `WorkerAgent(skills=…)` پیام سیستمی رو با `system_prompt(role, skills)` می‌سازه: دستورالعمل نقش، بعد بخش `## Skills` (به ترتیب فهرست نقش، هر Skill با نام، توضیح و بدنه، با تذکر اینکه Skill مجوزی نمی‌ده)، و در آخر `WORKER_PROTOCOL` ثابت. Skill گمشده یا مجموع بیش از ۶۰٬۰۰۰ نویسه قبل از هر فراخوانی مدل خطاست. `Role.policy()` فقط از `tools`/`max_risk` ساخته می‌شه و Skill روی اون اثری نداره (D44).
- **منبع Skillها در CLI (`skills/loader.py`):** `load_skills(workspace)` = Skillهای داخلی (`src/automa/skills/builtin/`، فعلاً خالی تا شاهد benchmark) + `<workspace>/skills/` (نبودن پوشه = خالی؛ symlink یا Skill خراب = خطای `SkillError` با پیشوند `workspace skills:`). نام مشترک بین دو منبع خطاست، نه جایگزینی. `automa new`، `automa run` و `automa bench run` این مجموعه رو قبل از ساخت پروژه یا هر فراخوانی مدل بارگذاری می‌کنن، به `RoleRegistry.builtin(skills=…)` برای بررسی وجود و به `WorkerAgent(skills=…)` (و `run_benchmark(skills=…)`) می‌دن؛ هر خطا کد خروج ۲ (تنظیمات) داره (D45).
- **نمایش در CLI:** `SkillOverview` در `cli.py` Skillها رو دقیقاً مثل `automa run` بارگذاری می‌کنه (داخلی + workspace، ادغام، بررسی با نقش‌ها) و منبع هر Skill و نقش‌های استفاده‌کننده رو نگه می‌داره. `automa skills [--json]` (نام، منبع، نقش‌ها، توضیح؛ JSON با `license` و `body_chars`) فقط‌خوندنیه و خطاش کد ۲ داره. `automa status` یک خط `skills:` نشون می‌ده و `status <id> --json` کلید `skills` (`available`، `roles`، `error`) داره؛ اینجا خطای Skill فرمان رو شکست نمی‌ده و فقط گزارش می‌شه (D46).
- **Skill برای نقش‌های داخلی از تنظیمات کاربر:** بخش `[roles.<name>]` در `automa.toml` فقط کلیدهای `skills` (فهرست نام) و `models`/`capabilities` (D97) رو قبول می‌کنه (`RoleSettings`، `extra="forbid"`؛ `tools`، `max_risk`، `tier`، `max_steps`، `instructions` و هر کلید دیگه خطای تنظیماته). `AutomaConfig.role_skills()` به `RoleRegistry(..., extra_skills=…)` (و `from_dir`/`builtin`) داده می‌شه که قبل از بررسی ابزار و Skill، نام‌ها رو به انتهای `skills` نقش اضافه می‌کنه و نقش رو دوباره با همه قوانین `Role` اعتبارسنجی می‌کنه (سقف ۸، نام معتبر، بدون تکرار). نقش ناشناخته (حتی با فهرست خالی) یا Skillی که نقش خودش داره خطاست؛ برابری `policy()` قبل و بعد دوباره بررسی می‌شه. `automa new`/`run`/`bench run`، `automa skills` و `automa status` همه از همین مسیر استفاده می‌کنن (D47).

- **دروازهٔ benchmark برای Skill خودکار (`src/automa/skill_gate.py`، D88):** `evaluate_skill_gate(baseline, candidate, benchmarks=, policy=)` خالص است و دو مجموعه رکورد benchmark (بدون/با Skill نامزد) را با حساب دقیق مقایسه می‌کند. قبول فقط اگر پوشش benchmarkها یکسان باشد، هر طرف دست‌کم `min_runs` اجرا داشته باشد، هیچ benchmarkی در نرخ قبولی یا میانگین امتیاز بدتر نشود، دست‌کم یکی اکیداً بهتر شود و (اختیاری) هزینه از `max_cost_ratio` برابر پایه بیشتر نشود؛ پس شرط «بهتر یا مساوی» بالا در کد به «بدون پسرفت و دست‌کم یک بهبود» سخت شده است. مقایسهٔ ناعادلانه (نسخهٔ متفاوت، تغییر تعریف benchmark، پروژهٔ تکراری، benchmark یک‌طرفه) خطاست. بدون مدل، نوشتن یا نصب؛ اجرای مقایسه‌ای، Agent نویسنده و CLI مراحل بعدی‌اند.

`<workspace>/selfdev/proposals/` (`sdp-*.json` و تصمیم‌ها `sdp-*.d<n>.json`، هر فایل یک‌بار با `os.link`) نگه می‌دارد و هنگام ذخیره دوباره با همان ROADMAP بررسی می‌کند (فقط SHA-256 آن و commit ذخیره می‌شود). پذیرفتن فقط تصمیم را ثبت می‌کند؛ هیچ چیز `ROADMAP.md` یا مخزن را نمی‌نویسد (`roadmap_line` خط دقیق را برای افزودن دستی می‌دهد). بدون مدل، شبکه یا پروسه. Agent پیشنهاددهنده (`src/automa/agents/proposer.py`، D85): `ProposalAgent.propose(vision_text, roadmap_text, budget_id=)` اول همه‌چیز را بدون مدل بررسی می‌کند (متن بودن ورودی‌ها، VISION ناخالی، ROADMAP معتبر با حداقل یک milestone، شناسهٔ بودجه با الگوی شناسهٔ پروژه)، بعد `proposal_digest` یک JSON قطعی و محدود (حداکثر ۴۸٬۰۰۰ نویسه؛ VISION حداکثر ۱۲٬۰۰۰؛ متن موردها ۴۰۰ ← ۱۶۰ نویسه ← حذف موردهای `[x]` با شمارش ← فقط نام milestoneها؛ `<`/`>` و کاراکترهای کنترلی/bidi escape) داخل `<repository>` می‌فرستد. هر فراخوانی از `LLMGateway` با BudgetGuard و به نام شناسهٔ بودجه (پیش‌فرض ثابت `selfdev-proposals`، تا سقف per-project روی همهٔ اجراهای پیشنهاد جمع شود) می‌رود؛ پاسخ نامعتبر یا بریده‌شده حداکثر `max_attempts` بار با بازخورد تکرار می‌شود و خطای gateway/provider بدون تکرار بالا می‌رود. نتیجه با `screen_proposals` روی **ROADMAP کامل** غربال می‌شود (پس موردی که از digest حذف شده هم دوباره پیشنهاد نمی‌شود) و `ProposalRun` (Screened، SHA-256 ROADMAP، تعداد تلاش) برمی‌گردد؛ رویدادهای `selfdev.proposals_ready`/`selfdev.proposals_rejected`. Agent هیچ چیزی نمی‌نویسد. فرمان `automa self propose [--repo] [--ref] [--roadmap] [--vision] [--json]` (D86): اول tier مدل و جای خالی `ProposalStore` (`check_room`) را بررسی می‌کند، بعد `read_commit_texts` (در `selfdev_project.py`) ROADMAP و VISION را از blobهای خام **یک commit** می‌خواند (همان قواعد امنیتی snapshot، بدون نوشتن هیچ فایل؛ سقف ۱MiB و UTF-8)، ROADMAP را parse می‌کند (خراب ← ۱۰)، و فقط بعد provider را می‌سازد و `ProposalAgent` را پشت `LLMGateway` + BudgetGuard (شناسهٔ بودجهٔ `selfdev-proposals`) اجرا می‌کند؛ رویدادها (هشدار بودجه و `selfdev.proposals_*`) در `<workspace>/selfdev/events.jsonl`. نتیجه با `ProposalStore.save` (همراه commit) ذخیره و هر پیشنهاد با شماره، milestone، خط دقیق `- [ ] …` و دلیل چاپ می‌شود؛ مخزن و ROADMAP هرگز نوشته نمی‌شوند و هیچ پروژه‌ای ساخته نمی‌شود. کدهای خروج: ۲ config، ۳ توقف بودجه، ۴ پاسخ معتبر نیامد، ۵ provider، ۱۰ ROADMAP خراب، ۱ بقیه (در همهٔ این‌ها چیزی ذخیره نمی‌شود). بازبینی (D87): `automa self proposals [SET_ID] [--json]` بدون شناسه همهٔ مجموعه‌ها را با شمارش pending/accepted/rejected فهرست می‌کند و با شناسه هر پیشنهاد را با شماره، وضعیت تصمیم، خط دقیق و دلیل نشان می‌دهد (فقط‌خواندنی؛ بدون config مدل، کلید یا نوشتن). `automa self accept|reject SET_ID N... [--yes]` همهٔ بررسی‌ها (مجموعه موجود و سالم، شماره‌های معتبر، یکتا و هنوز تصمیم‌نگرفته) را قبل از نوشتن انجام می‌دهد، پیشنهادها را کامل نشان می‌دهد و بعد از تأیید فقط فایل تصمیم یک‌بارهٔ `ProposalStore` را می‌نویسد؛ پذیرفتن خط‌های `- [ ] …` را زیر نام milestone برای افزودن دستی چاپ می‌کند. ROADMAP و مخزن هرگز خوانده یا نوشته نمی‌شوند و هیچ مسیری به provider/gateway ندارد.

## مجموعه آزمون (Benchmark)

پوشه `benchmarks/` شامل چند هدف نمونه با معیار موفقیت مشخصه. بعد از هر تغییر بزرگ، سیستم روی این‌ها اجرا می‌شه (در حالت واقعی، با بودجه محدود) و نتیجه در `benchmarks/results/` ثبت می‌شه. هیچ تغییری که نتیجه benchmark رو بدتر کنه نباید ادغام بشه.

**پیاده‌سازی (`src/automa/benchmarks/`):** هر benchmark یک فایل `benchmarks/<id>.toml` (مدل `Benchmark`، سخت‌گیرانه و تغییرناپذیر): `id` (الگوی شناسه پروژه، برابر نام فایل)، `title`، `kind` (`cli`/`web`/`research`)، `goal`، `answer` (جواب همه سؤال‌های روشن‌کننده در اجرای بدون کاربر)، `budget_usd` (بزرگ‌تر از صفر و حداکثر ۵)، `max_attempts` (۱ تا ۱۰) و `success_criteria` از نوع `AcceptanceCriterion` که **همه** باید `check` قطعی داشته باشن — موفقیت benchmark هیچ‌وقت با قضاوت مدل تعیین نمی‌شه. `BenchmarkSuite.from_dir` فقط فایل‌های `*.toml` سطح اول رو می‌خونه (`README.md` و `results/` نادیده) و مثل نقش‌ها بسته شکست می‌خوره (TOML خراب، symlink، غیرمعمولی، بیشتر از ۶۴KiB، غیر UTF-8، شناسه ناهمخوان، مجموعه خالی). `evaluate_benchmark(benchmark, files_dir, events)` همه معیارها رو با `run_criteria_checks` (همون مسیر بررسی قطعی Verifier) از یک `ToolExecutor` با `verifier_policy()` اجرا می‌کنه و `BenchmarkOutcome` (`passed`، `checks`، `score`؛ همیشه سازگار) برمی‌گردونه؛ این پکیج هیچ مدلی صدا نمی‌زنه و به `automa.llm`/`automa.budget` وابسته نیست (جزئیات: D26).

**اجراکننده (`src/automa/bench.py`، `automa bench run <id>`):** قبل از ساخت پروژه یا هر هزینه‌ای مجموعه، شناسه، تنظیمات، نگاشت سطح Executive، Provider، نقش‌ها و پوشه نتایج (`prepare_results_dir`) بررسی می‌شن. `run_benchmark` همیشه یک پروژه **جدید** با شناسه `bench-<YYYYmmdd-HHMMSS UTC>-<id>` (حداکثر ۶۴ نویسه) و هدف benchmark می‌سازه؛ یک `LLMGateway` با یک `BudgetGuard` که محدودیت‌هاش `benchmark_limits` هستن: سقف پروژه = `min(سقف کاربر، budget_usd)`، سقف هر فراخوانی تا همون پایین میاد و سقف روزانه دست نمی‌خوره — benchmark فقط می‌تونه محدودیت‌ها رو تنگ‌تر کنه. Executive سؤال‌هاش رو می‌پرسه و هر سؤال با `answer` ثابت benchmark جواب داده می‌شه، بعد `plan_project`؛ `Orchestrator` با `max_attempts` benchmark اجرا می‌کنه؛ در پایان، **هر طور که اجرا تموم شده باشه** (کامل، بودجه، Provider، شکست برنامه‌ریزی …)، `evaluate_benchmark` معیارها رو روی `files/` می‌سنجه. خروجی `BenchmarkRunRecord` (`src/automa/benchmarks/results.py`): `passed`/`score`/`checks` (فقط از بررسی‌های قطعی)، `stop` (دلیل توقف Orchestrator یا `planning`)، وضعیت پروژه، `budget_usd` مؤثر، `cost_nusd` و `model_calls` از Ledger، تعداد تلاش‌ها، وظایف passed/failed/blocked، زمان‌ها و نسخه Automa؛ مدل همیشه سازگاره. نتیجه write-once در `benchmarks/results/<id>/<project-id>.json` نوشته می‌شه (فایل موقت + `os.link`، بدون symlink). Ctrl+C نتیجه‌ای ثبت نمی‌کنه (پروژه `paused` می‌مونه و با `automa run` قابل ادامه‌ست). رویدادهای `benchmark.started`/`benchmark.finished` در `events.jsonl` پروژه (جزئیات: D27).

**benchmark تصویری (D104):** فیلد اختیاری `needs_images` (`StrictBool`، پیش‌فرض `false`) در `Benchmark`. `automa bench run` با `[images] model` همون `make_image_provider` اجرای عادی رو می‌سازه، خط `images:` رو چاپ می‌کنه و به `run_benchmark(image_provider=…)` می‌ده که روی **همون** BudgetGuard benchmark (سقف تنگ‌شده) یک `ImageGateway` برای Orchestrator می‌سازه؛ پس هزینهٔ تصویر در سقف benchmark و در `cost_nusd`/`model_calls` نتیجه حسابه. benchmark با `needs_images = true` بدون `[images] model` قبل از ساخت Provider، پروژه یا پوشهٔ نتایج با کد ۲ رد می‌شه (`run_benchmark` هم `ConfigError` می‌ده، قبل از ساخت پروژه)؛ Provider تصویر با تصویرِ خاموش هم `ConfigError`ه. `automa bench list` این benchmarkها رو با `[needs images]` نشون می‌ده. `landing-page-with-image` بررسی‌های قطعی فایل‌محور داره (یک `images/hero.png|jpg` واقعی هم‌قالب پسوند، حداقل ۲۵۶×۲۵۶، `<img>` نسبی با `alt`، بدون منبع بیرونی/`data:`).

**تحلیل شکست (`src/automa/benchmarks/report.py`، `automa bench report`):** `scan_results(results_dir, benchmark_id=None)` فقط می‌خونه: پوشه نتایج ناموجود = نتیجه خالی (چیزی ساخته نمی‌شه)، پوشه symlink/غیرپوشه = خطا؛ فایل‌های موقت `.…tmp` و فایل‌های پنهان نادیده؛ هر چیز دیگه‌ای که قابل اعتماد نیست (JSON نامعتبر، symlink، پوشه symlink، شناسه نامعتبر، رکوردی که `benchmark_id` یا `project_id`ش با مسیرش نمی‌خونه، فایل غیر `.json`، بیشتر از ۱۰۰۰۰ فایل) به‌صورت `ResultProblem` گزارش می‌شه، نه حذف بی‌صدا. `build_report(records, suite=…)` تابع خالصه و برای هر benchmark `BenchmarkSummary` می‌سازه: تعداد اجرا و قبولی، نرخ قبولی، میانگین امتیاز و تلاش‌ها، هزینه کل و میانگین (nano-USD)، شمارش `stop`ها، شمارش `FailureCause` (`criteria_missed` وقتی پروژه کامل شده ولی معیار benchmark رد شده — یعنی برنامه یا Verifier سهل‌گیر بوده)، معیارهای ردشده با توضیح از مجموعه (مرتب اول بر اساس رد در اجراهای کامل‌شده)، نسخه‌ها و آخرین اجرا. ماژول به مدل/بودجه وابسته نیست (همون تست ساختاری D26). جزئیات: D28.
